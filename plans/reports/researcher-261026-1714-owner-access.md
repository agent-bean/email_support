# Issue #5 owner access research

**Conducted:** 2026-10-26 (Asia/Bangkok)
**Scope:** Google OIDC for one configured owner; PostgreSQL-backed opaque browser sessions, sign-out, CSRF; exact backend/web change surface and focused TDD matrix. Constraints: `--hard --tdd --yagni`; no implementation, no multiuser support, no Redis.

## Recommendation

Use **Authlib 1.9.1+ Starlette/HTTPX2-compatible OIDC client primitives**, with a PostgreSQL OAuth-attempt record for one-use `state`, `nonce`, and PKCE verifier, and separate PostgreSQL-backed application sessions. Avoid relying on Authlib's default Starlette session storage for the login flow: the conventional Starlette `SessionMiddleware` stores signed session data in the browser. Keep provider code async; set/verify Google ID-token claims at the boundary and authorize by configured Google `sub`, never email alone.

Authlib is the best fit because its configured Starlette OAuth app offers async code exchange and an async `parse_id_token()` implementation that delegates signature/JWKS work to joserfc and claim checks to `CodeIDToken`; the framework convenience methods assume `request.session`, so the app must use the lower-level methods above for PostgreSQL-only transaction state. The current Authlib changelog says its HTTPX integration is powered by `httpx2`; this matches the repository's existing `httpx2>=2.16.0` dev dependency and avoids adding the unrelated `httpx` package. Add Authlib as a production dependency and add `httpx2` explicitly as a production dependency (Authlib 1.8+ uses it for its HTTPX integration; Authlib documents a deprecated fallback to `httpx` when `httpx2` is absent). Confirm the resolved dependency graph and lock/update rather than silently accepting fallback. Authlib 1.9.0/1.9.1 is recent (released Oct 14, 2026 per current PyPI/changelog), so pin the supported minor range and use its changelog/security advisories during upgrades; do not rely on old 1.5-era examples.

### Concrete Authlib 1.9.1 async OIDC path

The core `AsyncOAuth2Client.fetch_token(...)` exchanges the authorization code and returns token JSON; it does not validate an ID token. Authlib's concrete async validator is `parse_id_token()` on the configured `StarletteOAuth2App` (`oauth.google`), which uses `AsyncOpenIDMixin` and calls `CodeIDToken.validate()`. The safe composition can keep the one-use transaction in PostgreSQL: configure an ephemeral `OAuth` registry/client from fixed settings, generate state, nonce, and a PKCE verifier/challenge pair, then call `await google.create_authorization_url(redirect_uri, state=state, nonce=nonce, code_challenge=challenge, code_challenge_method="S256")`; persist the state, nonce, and verifier. Do not call the wrapper helpers `authorize_redirect(request)` or `authorize_access_token(request)`, because their Starlette mixin reads/writes `request.session`. In the callback, atomically consume the attempt, then call `await google.fetch_access_token(redirect_uri=..., authorization_response=<full callback URL>, state=<stored state>, code_verifier=<stored verifier>)` and `await google.parse_id_token(token, nonce=<stored nonce>, claims_options={"iss": {"values": ["https://accounts.google.com"]}, "aud": {"values": [<configured client_id>]}})`. Guard against missing ID token/`None` result, then compare the validated `sub` to `GOOGLE_OWNER_SUB`.

Authlib's current async parser fetches discovery metadata and `jwks_uri`, decodes the JWT signature with `joserfc.jwt` using a JWK key set and the discovery-advertised signing algorithms, retries once with a forced JWKS refresh on unknown `kid`, then calls `CodeIDToken.validate()`. `CodeIDToken` requires `iss`, `sub`, `aud`, `exp`, `iat`; validation also checks time claims, the supplied nonce, and `azp`. Include both `iss` and `aud` in explicit `claims_options`: Authlib uses its metadata issuer by default only when `claims_options` is omitted; supplying your own map replaces that default. The audience option binds `aud` to the configured client ID. Treat `sub` authorization as the application-specific check after token validation.

The official FastAPI/Starlette example uses `authorize_redirect(request)` and `authorize_access_token(request)`, which delegate state/nonce storage to `request.session`. There is no documented turnkey recipe for swapping only that storage to PostgreSQL. The lower-level async app methods above are the bounded composition point: externalize the transaction and manually orchestrate URL generation, code exchange, and ID-token validation. Add a focused contract test to prove this path never reads `request.session`.

**JWKS caveat:** The 1.9.1 async OIDC parser caches discovery/JWKS in `google.server_metadata` and forces one refresh on unknown `kid`; it exposes no TTL or response-size limit in this path. Reconstruct a fresh configured OAuth client for each request/flow, keeping metadata/JWKS lifetime to the callback validation and discarding the client afterward; this intentionally refetches metadata/keys per sign-in. Pin discovery to Google's known URL and validate its issuer; never derive metadata/JWKS URLs from callback input. Bound async connection/read timeouts and metadata/JWKS response size at the HTTP transport or egress boundary, and fail closed on oversized responses, unsupported algorithms, or unknown keys after Authlib's single refresh. If a process-wide client/cache is later chosen, it needs an explicit finite refresh/expiry policy. Test unknown `kid`, successful rotation refresh, and oversized/slow provider responses against controlled endpoints.

Official references: [Authlib HTTPX2 async OAuth client](https://docs.authlib.org/en/latest/oauth2/client/http/httpx.html), [Authlib FastAPI integration](https://docs.authlib.org/en/latest/oauth2/client/web/fastapi.html), [Authlib Starlette integration](https://docs.authlib.org/en/latest/oauth2/client/web/starlette.html), and version-pinned [Starlette app](https://github.com/authlib/authlib/blob/v1.9.1/authlib/integrations/starlette_client/apps.py), [async OAuth app](https://github.com/authlib/authlib/blob/v1.9.1/authlib/integrations/base_client/async_app.py), [async OIDC parser](https://github.com/authlib/authlib/blob/v1.9.1/authlib/integrations/base_client/async_openid.py), and [`CodeIDToken` claims](https://github.com/authlib/authlib/blob/v1.9.1/authlib/oidc/core/claims.py).

### Trade-offs

| Choice | Async fit | Complexity | Maintenance/security | Project fit |
|---|---|---|---|---|
| **Authlib + explicit PostgreSQL transaction/session records (recommended)** | Native async Starlette client and current HTTPX2 backend | Moderate: persist/consume protocol transaction values explicitly | Mature protocol library; recent release requires version-aware API review | Fits FastAPI/SQLAlchemy async, and can keep both browser auth session and OAuth attempt server-side |
| `google-auth` ID-token verification + hand-built OAuth protocol | Verification helper is synchronous and accepts a sync transport; async web path needs an adapter/thread hop or another verifier | Highest: OAuth redirects, token exchange, state/nonce/PKCE, JWT/JWKS cache all become app-owned | Google-maintained verifier is authoritative but hand-built protocol increases correctness burden | Poorer async and maintainability fit than Authlib |
| Authlib Starlette integration + `SessionMiddleware` | Native async | Low initially | Browser holds signed session payload; requires secret rotation/config and does not provide the requested PostgreSQL server-side session semantics | Can support OAuth library state only if session handling is replaced/adapted; not recommended as the app session design |

## Security and flow decisions

1. **Owner identity and bootstrap.** Require a configured `GOOGLE_OWNER_SUB` plus OAuth client ID/secret, fixed HTTPS redirect URI, and a trusted frontend origin. Fail closed for authentication when required configuration is missing; a deployment preflight should report misconfiguration without making import, OpenAPI generation, or the independent liveness endpoint require credentials. Bootstrap the owner `sub` out-of-band from a verified Google identity under operator control; do not let first visitor, email address, or OAuth callback auto-enroll. Compare the verified ID-token `sub` to the configured value on every sign-in. `email` can be displayed/audited but is mutable and must not be the identity key. On provider-consent callback, require the verified Google `sub` to equal the configured owner (same identity), while retaining distinct login and consent endpoints/scopes.

2. **OIDC transaction.** On `/auth/google/login`, create independent high-entropy state, nonce, and PKCE verifier (`S256`); store required transaction material and fixed return target in a short-lived OAuth-attempt row. Redirect only to configured Google endpoints/redirect URI. On callback, atomically claim/delete the live attempt matching state before token exchange; reject missing, expired, reused, or mismatching state. Use the explicit Authlib async URL-generation/code-exchange/`parse_id_token()` sequence above with the stored verifier and nonce; validate signature against Google's JWKS, issuer, exact client-ID audience, `exp`/`iat`, and nonce. State, nonce, and PKCE solve different checks; retain all three. The documented Starlette convenience flow uses `request.session`, so avoid those wrappers when transaction state must remain in PostgreSQL.

3. **Session token/store.** Generate a 256-bit opaque CSPRNG session secret, store its SHA-256 digest in PostgreSQL, and give the browser only the raw secret in the cookie. Use the selected 12-hour expiry policy, rotate the session on successful login, and delete/invalidate it on logout. Cookie: `HttpOnly`, `Secure` in production, `SameSite=Lax` for cross-site OIDC top-level GET callback compatibility, `Path=/`, no `Domain`, bounded `Max-Age`; clear it on logout/expired session. Never place tokens in URLs, localStorage, logs, or OpenAPI examples.

4. **CSRF.** For every cookie-authenticated unsafe method, verify a synchronizer token bound to the server session (header for JSON APIs; form/header where applicable); reject absent/invalid tokens. Expose the token through an authenticated same-origin bootstrap endpoint or a response header that the frontend can read; do not put auth credential in JS-readable storage. Also reject cross-origin `Origin` on state-changing browser requests (allowlist exact frontend origin) and use SameSite as defense in depth, not the only control. OAuth callback state is separate from application CSRF token. `GET /health` remains public, database-independent and provider-independent.

5. **OpenAPI/import/health boundary.** Importing `email_support.main:app` must not require Google secrets, make network calls, or connect to PostgreSQL. Auth routes/dependencies can be composed at app startup but settings validation and DB resources should be explicit lifespan/composition concerns; the existing lazy engine factory already supports no-connect construction. Mark OAuth redirect/callback and cookie/session endpoints deliberately in OpenAPI (hide protocol endpoints if they are implementation-only, but do not hide protected application contracts). Keep `/health` unauthenticated and dependency-free; authenticated route dependencies fail closed when configuration/session is unavailable.

## Focused TDD matrix

| Layer | First failing behavior to encode | Required assertions |
|---|---|---|
| OIDC service/unit | Wrong Google identity attempts sign-in | Correct signature/issuer/audience/expiry/nonce passes; `sub` mismatch rejected even if email matches; email change with matching `sub` remains same owner |
| OIDC transaction/unit + DB | State/nonce/PKCE replay or timeout | State is unpredictable, PKCE method S256, callback consumes transaction exactly once atomically, expiry/missing/mismatch/replay rejected |
| Session persistence/integration | Cookie/session expiration and logout | Cookie contains opaque secret only; persisted record stores SHA-256 digest, never raw secret; selected 12-hour expiry enforced; logout invalidates; pre-login session cannot survive rotation |
| API/dependency integration | Protected route without valid session / unsafe request without CSRF | unauthenticated gets 401; bad/expired/revoked session rejected; missing/wrong CSRF on POST/PATCH/DELETE rejected; valid token succeeds; safe GET remains usable |
| App composition/contracts | Runtime secrets or DB/provider access during import/OpenAPI/health | Import succeeds without auth secrets/network/DB; OpenAPI emits expected protected route contracts and no credential values; `/health` succeeds without login, DB or Google calls |
| Web feature | Signed-out and expired responses | Login affordance shown while signed out; expired session returns to useful signed-out state; browser sends CSRF token with mutations and keeps no credential in localStorage |

Use no Google live call in tests. Use a controlled issuer/JWKS/token endpoint or a narrow provider-boundary fake; use the real PostgreSQL test fixture for uniqueness, expiry, revocation, and concurrent one-use transaction claims. Do not test library internals.

## Limits and unresolved questions

No issue implementation or dependency resolution was performed. The exact Authlib/httpx2 constraint still needs resolution against the repository's lock/tooling before implementation. The current Authlib JWKS cache has no documented TTL; implementation must add a finite refresh policy around the client metadata cache. Bootstrap procedure for supplying the owner's Google `sub` is an operations choice; the security requirement is that it is operator-controlled and never self-enrolled from an unauthenticated first visit. The issue's acceptance criteria are backend plus web; this report's proposed code detail focuses on backend access primitives.
