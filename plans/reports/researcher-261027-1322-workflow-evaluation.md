# Research: resumable briefings and evaluation design

**Conducted:** 2026-10-27 (Asia/Bangkok)
**Scope:** Joint planning evidence for Issues [#9](https://github.com/agent-bean/email_support/issues/9), [#13](https://github.com/agent-bean/email_support/issues/13), and [#32](https://github.com/agent-bean/email_support/issues/32). The worktree was inspected read-only; no provider, database, migration, or GitHub mutations were run.

## Recommendation

Implement one typed LangGraph `StateGraph` and invoke it through the same application composition path from the bounded local command and evaluation runner. Persist source evidence and immutable briefing versions through the existing SQLAlchemy/Alembic persistence boundary; use `langgraph-checkpoint-postgres` only for resumable graph execution state. A stable `thread_id` should identify one briefing workflow execution, with application-level ownership preventing duplicate or concurrent runs/resumes. The graph must persist the draft before it interrupts; the deterministic approval service remains authoritative when authenticated review/resume is added.

For quality evaluation, record atomic factual claims with evidence IDs and separately label suggestions. Use reviewed, versioned source snapshots and claim-level expected evidence maps. The evaluator can deterministically check evidence references, required/forbidden claim IDs, workflow events, and application invariants; it must not claim to prove semantic entailment by exact text matching. Human review is the authority for whether free-text claims are actually supported and whether the briefing is useful. An LLM judge can help prioritize review, but cannot certify those facts or any permission.

## LangGraph state, updates, and roles

The Graph API accepts `TypedDict` or Pydantic graph state; its documented conventional choice is `TypedDict`, with Pydantic available where recursive validation is needed. Reducers are per-channel update rules: ordinary fields take the latest write, while list accumulation needs an explicit reducer such as `operator.add`. In parallel branches, use narrow partial update dictionaries and explicit reducers only for independently appended evidence/trace collections. Do not use list concatenation for identity, company resolution, or “current draft” fields. Validate business results and the final graph result with existing Pydantic contracts, since a typed annotation is not runtime validation of every node update. [Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api) documents the state and reducer model; local standards make the validation requirement explicit.

Suggested state categories (not a new persisted schema commitment):

| Category | Contents / rule |
|---|---|
| Inputs | Stable briefing/run UUID, normalized email and meeting, fixed scenario time/timezone, explicit context availability. Keep identifiers bound; do not use company ID as the thread ID. |
| Identity/context | Typed company/contact resolution, approved prior knowledge if supplied, and explicit `absent` vs `unavailable/error`. Empty history is valid and creates no retrieval hit. |
| Evidence | Typed source records with evidence ID, URL or source kind, retrieval/publication time where available, snapshot/version, and retrieval outcome. Keep evidence append-only through a reducer if graph branches add separate evidence. |
| Draft/result | Claim-level factual statements with cited evidence IDs, separate recommendations/questions, uncertainty/unknowns, and rendered Markdown. Persist the canonical briefing version via service before interrupt. |
| Control/trace | Non-secret role/tool/provider event IDs, status, duration, failure category and available provider usage. Trace metadata must not contain complete email bodies or credentials. |

Keep the graph small and match roles to real work: deterministic input/context validation and persistence; Web Research Agent using only Issue #9’s bounded read-only tools; Report Generation Agent synthesizing cited evidence; deterministic Human Approval Agent recording pending decision and interrupt. “Role” is an auditable responsibility boundary, not a requirement for a separate service or an extra model call. No node or model-callable tool can approve, send, or promote knowledge. Suggestions must have a distinct type/section from verifiable company facts.

## PostgreSQL checkpointer and restart semantics

LangGraph’s checkpointer stores thread-scoped graph snapshots and node writes. A `thread_id` is the key used to find the latest checkpoint; resume must reuse that ID. The saver is separate from the LangGraph Store (cross-thread durable memory), and neither replaces canonical application tables. Use the canonical briefing ID or a dedicated stable run UUID as `thread_id`, and persist the mapping to the canonical briefing/job context in application-owned data. Never identify a run by company alone.

Current primary docs specify `AsyncPostgresSaver` from the separately installed `langgraph-checkpoint-postgres` package. `ainvoke`/`astream` needs the async saver. Its documented `from_conn_string` opens a Psycopg `AsyncConnection` with `autocommit=True`, `row_factory=dict_row`, and `prepare_threshold=0`; a supplied connection/pool must satisfy library requirements. `setup()` creates its own `checkpoints`, `checkpoint_writes`, and `checkpoint_migrations` tables and applies its internal migration sequence. It must run before the first graph use. `setup()` is not an Alembic migration and it does not automatically join the application’s SQLAlchemy transaction. [Official package README](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/README.md), [current async implementation](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/langgraph/checkpoint/postgres/aio.py), and [checkpointer docs](https://docs.langchain.com/oss/python/langgraph/checkpointers) cover these behaviors.

**Schema ownership needs an explicit implementation decision.** Recommended: create a dedicated checkpoint schema and permissions in an Alembic migration, set the checkpointer connection’s `search_path` to that schema, and call saver `.setup()` idempotently from an explicit worker/application bootstrap or lifespan point. This lets Alembic own the schema boundary and the library own its private checkpoint tables/migration counter, avoiding hand-copying upstream DDL into migrations. Verify with the chosen driver URL and actual schema-qualified behavior before relying on it; do not assume `postgresql+psycopg://` SQLAlchemy URLs can be passed unchanged to Psycopg. Alternative: use the default schema and let `.setup()` create unqualified tables, which is simpler but weakens migration ownership and risks collisions. In either design, tests need to prove setup is repeatable and migration/user tables do not collide.

Call `setup()` as an explicit schema-bootstrap operation, not from each invocation and not hidden in graph construction. Keep a long-lived async saver/pool at the process composition boundary and close it on shutdown; do not share a single caller-owned SQLAlchemy `AsyncSession` with graph nodes or let a provider/storage module import graph orchestration. The checkpointer captures serialized state, so minimize/check privacy of its contents and configure safe MessagePack deserialization per the saver’s security guidance. Checkpoint retention must be revisited before production because snapshots and node writes accumulate; pruning is operational policy, outside these three issues unless required for safe initial bounds.

`interrupt()` serializes a JSON-compatible request and persists state. Resume uses `Command(resume=validated_decision)` with the *same* thread ID. The node containing the interrupt starts again from its beginning; therefore do no work with non-idempotent effects before the interrupt call. Here, persist the draft first, then interrupt with only a small review reference/payload. On restart, reconstruct the graph with compatible code/config and same checkpointer, inspect pending interruption, and resume only after the authenticated review interface has validated a decision bound to the exact briefing version. A stale/missing decision is rejected by application services. LangGraph documents that an interrupt waits indefinitely and the node is restarted on resume. [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts).

Do not run concurrent starts/resumes for the same thread. The checkpointer’s `thread_id` is a lookup coordinate, not an application ownership lease or authorization control; current OSS graph docs do not promise serialized concurrent invocations on one thread. Use the application job lease/CAS/briefing status transition to claim that stable run and fence stale workers, and serialize the review/resume transition through the approval service. Even `durability="sync"` means checkpoint writes happen before the next graph step; it does not by itself provide a cross-process per-thread lock. For this initial workflow, bounded explicit execution can avoid fan-out entirely. Test concurrent-claim rejection with real PostgreSQL before adding parallel branches.

Durability modes matter at node boundaries: `sync` persists a step before continuing (strongest crash behavior, with latency cost); `async` persists while the next step runs (small process-crash loss window); `exit` writes at graph completion/interrupt/error, so it cannot recover mid-run. Given “persist draft and pending review across restart,” use `sync` for the bounded local and reviewable run unless measured cost later justifies another setting. Keep external side effects after the decision and application-owned idempotency/uncertain-outcome recovery; checkpoint replay or resume does not make provider effects exactly-once.

## Evaluation design: what it can and cannot prove

Long-form briefing prose mixes facts, unsupported details, and suggestions. FActScore’s peer-reviewed work motivates atomic claim-level scoring rather than treating a whole answer as simply correct/incorrect; however, its automated method still uses retrieval and a strong LM to label support. It is a useful methodology reference, not proof that a model judge is authoritative for this application. [FActScore, EMNLP 2023](https://aclanthology.org/2023.emnlp-main.741/).

Use four labels with explicit meanings: **supported** (the reviewed snapshot supports this atomic claim), **unsupported** (the provided evidence does not support it; this does not necessarily mean the claim is false), **unknown** (evidence is absent, stale, conflicting, or publication/retrieval state cannot resolve it), and **suggestion** (recommendation/question, not a factual assertion). Store output claim text, claim kind/label, evidence IDs, and source snapshot IDs. Case data stores reviewed expected fact IDs and expected evidence IDs/labels. A deterministic evaluator checks:

1. Every factual output claim references existing evidence IDs in the same case/run; no unknown or out-of-scope IDs.
2. For explicitly reviewed fact IDs, actual evidence IDs/status match the reviewed case map; known unsupported/forbidden atoms are surfaced as failures, not rescued by fluent prose or a citation URL alone.
3. Suggestions are not counted as facts, while material date/identity assertions cannot be mislabeled as suggestions to evade support checks.
4. Missing expected facts, unresolved unknowns, ambiguity, and unsupported claims are reported separately; unreviewed and unsupported-feature cases are `not evaluated` or `unsupported`, never passes.

Do not compare claim text to excerpts using substring/string similarity as entailment. A deterministic checker can establish referential integrity and compare reviewed atomic fact IDs/evidence bindings; it cannot decide that an arbitrary paraphrase is entailed by a web excerpt. Human review of generated claim/evidence pairs remains required for gold support and meeting usefulness. The real evaluator self-check should use a tiny, fixed, *reviewed* fixture containing one supported atomic claim tied to a valid snapshot and one explicitly unsupported/forbidden claim with no supporting evidence; run the production evaluator over those records and assert the two outcomes differ. This self-check validates evaluator logic, not model quality or general semantic entailment. Keep any scripted/provider-double test labeled as contract/replay only.

Quality results should separately report support on reviewed applicable claims, required-fact coverage, unsupported/unknown rates, company-identity correctness, retrieval relevance, human usefulness/task completion, scenario outcome, and case status (reviewed, unreviewed, unsupported feature). Add latency, tool trace, model/prompt/configuration and provider usage only when observable; missing usage is `unknown`, not zero. Report per-case evidence and failures before any aggregate. Don’t pick quality thresholds from illustrative numbers: establish baselines with owner-reviewed cases.

### Execution/replay/live split

- **Evaluator self-check:** No assistant/provider. Exercise the exact deterministic evaluator/report aggregator against fixed reviewed claim/evidence records, proving supported differs from unsupported. It checks code behavior only.
- **Offline graph regression:** Run the production workflow factory, persistence path, and typed tool/provider boundaries against fixed normalized scenario inputs, source snapshots, and scenario clock. At the provider boundary, prerecorded/deterministic responses may prove contract and reproduce a captured run; report this as replay/contract evidence, not fresh model quality. Use the same graph, role/tool allowlists, claim-output contract, persistence and trace hooks. Do not create a second “evaluation assistant.”
- **Opt-in live evaluation:** Invoke the same factory and graph with actual configured gateway/search/integration adapters. Bound scenario count, duration, retries and cost; pin or record model/prompt/adapter/source versions. Record changed live sources and actual provider usage, preserve content privacy, and mark the live case incomplete on missing required provider capability. It is not a release pass until required cases are supported and owner-reviewed.

### Issue #8 acceptance and exact repository evidence

Issue #8 (“Interpret email and resolve company context”) requires: distinguish relevant/irrelevant mail; return validated company/contact candidates, needs, evidence, and ambiguity without treating sender assertions as verified identity; resolve repeated inputs stably without silent merges from public/shared domains, similar names, or missing identity; persist owner corrections through typed service operations and apply them to future lookup; let the initial local workflow use the operations without an unauthenticated HTTP endpoint; and evaluate relevant/irrelevant mail, ambiguity, and incorrect prior associations separately from report quality.

Current schema evidence narrows the design:

- `ContactRow` has a globally unique expression index over the email local-part plus lowercased domain; the Pydantic normalizer also lowercases only the email domain. The local part remains case-sensitive by design. `ContactRow.company_id` is nullable, mutable, and FK-constrained. There is no storage operation to look up a contact by email; only UUID `get_contact` and insert `create_contact` exist.
- `CompanyRow.name` and `CompanyRow.domain` are non-unique; neither can serve as an identity key. Similarity/name/domain matches can create candidates only. A public domain or duplicate domain must remain ambiguous.
- `MailMessageRow` is unique by `(account_id, external_message_id)`. `MailMessageCreate` requires a real `account_id`, and there is no idempotent get-or-create by provider key. Provider account identity itself is unique on `(provider, external_account_id)`. Do not invent “local” provider accounts or external message IDs to fit local/eval inputs into those provider-provenance rows.
- `MailMessageRow` has independent nullable `contact_id` and `company_id` FKs. Thus correcting `ContactRow.company_id` alone does not rewrite historical message associations. Company Info must validate current contact identity before making those messages eligible as context; a cached `mail_messages.company_id` is not authoritative after a correction.

### Smallest stable interpretation and identity behavior

Define one provider-neutral normalized email/meeting input contract for the interpreter and local workflow. Keep source provenance explicit and discriminated: local input carries its stable local/case input ID; provider-backed input carries the actual provider account/message or calendar/event reference. Provider adapters map their native record into this normalized contract; they do not change its semantic fields. Local and synthetic evaluation input gets no fabricated provider-account identity. Evaluate against a separate evaluation database/fixture boundary so synthetic contacts/company records cannot pollute operational canonical records. The existing `MailMessageCreate`/`MeetingCreate` remain the persistence contracts for actual provider-backed records; do not weaken their required provider identity to make test fixtures fit.

Use exact normalized full sender email as the stable contact lookup key. Add a storage query using the existing email expression index and an idempotent contact get-or-create that creates new contacts with `company_id=None`. Repeated identical provider events are keyed by the existing `(account_id, external_message_id)` uniqueness when real ingestion is added; for normalized local inputs, reuse their stable input ID. No name or domain similarity creates/merges a company or contact. A company name/domain inferred by the interpreter is an untrusted candidate with evidence/provenance and ambiguity, never an update to canonical identity. An existing contact-to-company mapping is the only automatic identity association; otherwise leave company unresolved until independent evidence plus explicit owner correction. This deliberately sacrifices automatic association of a new sender at a valid company domain, avoiding accidental binding of shared domains or subsidiaries.

Owner correction should be a single typed service operation (for example, `correct_contact_company(contact_id, company_id | None)`) backed by an explicit persistence update to the existing `ContactRow.company_id`. That row is the smallest durable override, with no need for a generic alias registry or a company-merge framework. Validate that both rows exist, allow `None` to clear a wrong association, and make correction the sole path that changes the mapping. The model/interpretation result cannot overwrite it, even if subsequent runs produce another candidate. The local CLI can call the same typed service with an owner-supplied correction; do not expose unauthenticated HTTP or UI for #8. Future authenticated review can call the same service.

For stale in-flight input, add one monotonically increasing `identity_revision` to contacts (defaulted in an Alembic migration). Increment it only when the explicit correction changes the mapping. At interpretation start, capture `{contact_id, company_id, identity_revision}` in the typed normalized workflow input. Before persisting a briefing as reviewable, before interrupting, and before resuming a checkpoint, re-read/compare that snapshot in the canonical persistence transaction. If the revision changed, reject the old result as `StaleIdentityInput`, do not expose it as current/pending review, and rebuild from corrected context under a fresh workflow attempt/thread. On a corrected mapping to `None`, retain the contact as unresolved and exclude all company-specific history from it.

Company-context eligibility should be conservative: use only records attached to the exact currently selected `company_id`; include a contact’s history only when that contact’s current explicit mapping still equals the selected company. Ignore stale `mail_messages.company_id` associations when they disagree with the current contact mapping. Never promote a company merely because a message body/sender claims it. A new, ambiguous, public-domain, or missing-identity input gets no company-specific history. Company matching by name/domain remains a candidate list requiring explicit resolution. A correction from A to B changes future lookups to B and makes A-associated records from that contact ineligible; it does not silently migrate old email records to B.

### Advisory-lock counsel: checkpointer writes cannot be fenced by a separate lock connection

A session-level PostgreSQL advisory lock is owned by one physical database session and is automatically released when that session ends. SQLAlchemy `AsyncConnection` holds a pooled connection while checked out and exposes its underlying Psycopg connection only through a driver-level proxy; SQLAlchemy documents that proxy as connection access, not as a supported way to hand one live connection concurrently to two transaction/session managers. LangGraph’s Postgres saver owns or receives its own Psycopg connection/pool and writes checkpoints through that connection. Therefore, **a lock held on a SQLAlchemy connection does not fence checkpoint writes sent over a separate saver connection**. If the SQLAlchemy lock session dies, a surviving saver connection can still write stale checkpoints. [PostgreSQL advisory-lock semantics](https://www.postgresql.org/docs/current/explicit-locking.html), [SQLAlchemy async raw-connection contract](https://docs.sqlalchemy.org/en/21/orm/extensions/asyncio.html), [LangGraph async saver](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/langgraph/checkpoint/postgres/aio.py).

Do not create an in-process hybrid that borrows `get_raw_connection().driver_connection` into `AsyncPostgresSaver` while SQLAlchemy also manages the same physical Psycopg session. That crosses two transaction managers, can break autocommit/row-factory assumptions, and is not an established integration contract. Session advisory locks also do not survive the intentional human pause; holding a DB connection while a graph awaits review for an arbitrary duration is not valid.

The narrow, honest protection is an identity revision/CAS at canonical boundaries, not pretending that an advisory lock is a lease: store the revision snapshot in graph state; before creating a sealed/current review version or accepting a resume, transactionally compare it with the contact’s live revision and reject stale work. A stale checkpoint may still be written to its old thread, but it is non-authoritative, cannot become canonical/reviewable, and must never be resumed after the revision mismatch. Start fresh with a new attempt/thread ID from the corrected input. Keep each canonical correction/publish transaction short; a transaction-level advisory lock or row lock on the contact can serialize the compare-and-update inside that transaction, but must not span model/provider calls. If later worker leasing is already supplied by a previously selected jobs issue, use it for worker ownership; do not add a general lease subsystem to #8.

Specific tests: (1) save normalized input at revision N, correct contact to revision N+1, then prove old graph output cannot be sealed/offered for review or resumed; (2) run correction and final canonical write concurrently and prove one obtains a consistent database order and no result with stale N becomes reviewable after N+1 commits; (3) terminate the lock connection while a saver connection can still write, demonstrate that checkpoint data is treated as stale/non-authoritative on the next gate; (4) resume an unchanged revision after process reconstruction successfully with the same thread. The third test documents the actual boundary instead of asserting an unsupported cross-connection lock guarantee.
